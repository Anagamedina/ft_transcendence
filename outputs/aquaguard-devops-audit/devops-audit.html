2. Mejoras recomendadas

Orden de diseño recomendado para que el flujo sea mantenible y no esconda decisiones peligrosas.

Contrato único de entorno

Definir variables requeridas por servicio, valores por defecto solo para local y validación temprana. SECRET_KEY debe ser distinto del placeholder en producción; validar COOKIE_SECURE, hosts, puertos y CORS.

Compose por capas

Mantener una base común y un override de desarrollo que añada puertos, volúmenes y frontend Vite. El perfil sim debe ser explícito y operable, no una promesa vacía.

Migraciones seguras

Arranque: comprobar configuración, esperar DB y ejecutar upgrade head en local. Desarrollo: alembic check detecta cambios sin migración. Generar autogenerate solo bajo un target manual y con revisión.

Readiness real

Conservar /api/health para liveness y usar /api/health/db para readiness. El gateway, simulador y smoke tests deben depender de la señal correcta.

Reproducibilidad

Instalar dependencias con lockfiles; frontend ya usa npm ci en gateway. Para Python, considerar constraints/lock y una imagen de desarrollo separada con pytest, lint y formatter.

CI operativa

Validar Compose, construir imágenes, ejecutar tests/lint, comprobar migraciones contra Postgres efímero y hacer smoke de /api/health y /api/health/db.

Política de Alembic

Arranque local

alembic upgrade head tras esperar DB. Es determinista y no crea archivos.

Detección

alembic check en make migration-check, con base levantada. Si falla por conexión, reportar prerequisito, no “sin drift”.

Creación

make migration MSG="..." ejecuta revision --autogenerate solo por petición explícita. Nunca desde entrypoint.

Ejemplo de interfaz

COMPOSE := docker compose
DEV_FILES := -f compose.yaml -f compose.dev.yaml
.PHONY: help setup dev up down restart build migrate migration migration-check seed smoke doctor logs shell test lint format clean reset-db

up: env certs config-check
	$(COMPOSE) up --build -d
	./scripts/wait_for_stack.sh

migrate: config-check
	$(COMPOSE) exec backend alembic upgrade head

migration-check: config-check
	$(COMPOSE) exec backend alembic current --check-heads
	$(COMPOSE) exec backend alembic check

migration:
	@test -n "$(MSG)" || (echo 'Uso: make migration MSG="descripcion"' >& exit 2)
	$(COMPOSE) run --rm backend alembic revision --autogenerate -m "$(MSG)"

seed: migrate
	$(COMPOSE) exec backend python -m seeds.seed_demo

4. Scripts auxiliares necesarios

Extraer lógica evita targets frágiles y permite reutilizarla en Compose, CI y diagnóstico local.

Qué no debe hacer un script de arranque

No autogenerar migraciones

La generación automática cambia el repositorio y puede ocultar una decisión de esquema. Debe ser una acción manual y revisable.

No instalar dependencias a ciegas

setup puede verificar o preparar explícitamente. El arranque de producción no debería ejecutar npm install ni modificar lockfiles.

5. Flujo de arranque recomendado

Propuesta para que make dev sea predecible tanto en el primer uso como en los siguientes.

01 · DOCTOR

Herramientas

Verificar Docker Compose, OpenSSL, Node/npm si se usa frontend local y disponibilidad de puertos.

02 · CONFIG

Entorno

Crear .env solo si falta; validar variables y no imprimir secretos. Preparar certificado local idempotente.

03 · BUILD

Imágenes

Construir backend y gateway; excluir .env anidados y artefactos locales del contexto.

04 · DB/API

Arranque

Levantar Postgres, esperar health; backend aplica upgrade head y publica liveness/readiness.

05 · VERIFY

Validación

Esperar readiness, comprobar migración, ejecutar smoke y mostrar URLs/logs. Seed solo si se solicita.

Primera ejecución

make setup → revisión manual de .env → make dev → make smoke. Si se necesitan datos demo: make seed. No borrar el volumen para “arreglar” un fallo sin diagnóstico.

Ejecuciones posteriores

make dev debe ser idempotente: reutilizar volumen, aplicar solo migraciones pendientes, esperar health y mantener logs accesibles. make migration-check se ejecuta antes de crear una PR.

CI

Levantar Postgres efímero, instalar dependencias bloqueadas, ejecutar alembic upgrade head, alembic check, tests y smoke. Fallar si faltan migraciones o hay drift.

Producción

Preferir job de migración versionado y único antes de nuevas réplicas. El entrypoint de la API no debería ser el coordinador de schema en un despliegue multi-réplica.
